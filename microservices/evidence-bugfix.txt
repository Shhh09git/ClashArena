Bug 1 (found 31 Aug 2026): NoneType error in leaderboard-service when
creating new leaderboard entries. Fixed by explicitly setting
rating=1000 on creation instead of relying on the SQLAlchemy default,
which isn't applied until the row is flushed.

Bug 2 (found 5 Sep 2026, during a documentation review): the original
version of this evidence file actually demonstrated a *different* bug,
not a successful test. tournament-service had no check preventing a
player from registering twice for the same tournament. When that
happened by accident, the bracket paired a player against themselves,
and the leaderboard below showed only one player with both a win and
a loss - proof of the duplicate-registration bug, not proof the
pipeline works correctly.

Fix: added a duplicate-registration check to
microservices/tournament-service/app.py's register_for_tournament(),
matching the guard the monolith already had.

Bug 3 (found 6 Sep 2026): event_id was a random uuid4() generated
fresh on every report, so a genuinely replayed result would never be
recognised as a duplicate by ingestion-service's de-duplication logic
(only the separate status == "reported" check on tournament-service
was actually preventing double-counting). Fixed by making event_id
deterministic: f"match-{match.id}-result", so the same match always
produces the same id.

=== Verification run, 6 Sep 2026 (after all three fixes) ===

1. Registered org_v2 (organizer), p1_v2, p2_v2 as separate users.
2. Logged in as p1_v2, registered for tournament 1 - succeeded.
3. Logged in as p2_v2, registered for tournament 1 - succeeded.
4. Started the tournament:
   {"players":2,"status":"in_progress"}
5. Bracket correctly shows two distinct players:
   {"id":1,"player1_id":2,"player2_id":3,"round":1,"status":"pending","winner_id":null}
6. Reported the result (p1_v2, id 2, wins 2-0). Note the event_id is
   now deterministic, not a random UUID:
   {"event_id":"match-1-result","status":"reported","winner_id":2}
7. Leaderboard correctly shows both players:
   [{"losses":0,"rating":1020,"username":"p1_v2","wins":1},
    {"losses":1,"rating":990,"username":"p2_v2","wins":0}]

This confirms: (a) duplicate tournament registration is now rejected,
(b) the result-ingestion pipeline correctly processes a result between
two distinct players end to end, and (c) event_id is now deterministic
per match, so ingestion-service's de-duplication logic can genuinely
catch a replayed result rather than relying solely on the separate
status check in tournament-service.
