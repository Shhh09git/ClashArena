Bug 1 (found 31 Aug 2026): NoneType error in leaderboard-service when
creating new leaderboard entries. Fixed by explicitly setting
rating=1000 on creation instead of relying on the SQLAlchemy default,
which isn't applied until the row is flushed.

Bug 2 (found 5 Sep 2026, during a documentation review): the original
version of this evidence file actually demonstrated a *different* bug,
not a successful test. tournament-service had no check preventing a
player from registering twice for the same tournament. When that
happened by accident, the bracket paired a player against themselves,
and the leaderboard below showed only one player with both a win and
a loss - proof of the duplicate-registration bug, not proof the
pipeline works correctly.

Fix: added a duplicate-registration check to
microservices/tournament-service/app.py's register_for_tournament(),
matching the guard the monolith already had. Verified below with two
genuinely distinct players.

=== Verification run, 5 Sep 2026 ===

1. Registered org_final (organizer), alice_f, bob_f as separate users.
2. Logged in as alice_f, registered for tournament 1 - succeeded.
3. Registered alice_f for tournament 1 a second time - correctly
   rejected:
   {"error":"already registered"}   (HTTP 409)
4. Registered bob_f for tournament 1 - succeeded (once).
5. Started the tournament:
   {"players":2,"status":"in_progress"}
6. Bracket correctly shows two distinct players:
   {"id":1,"player1_id":2,"player2_id":3,"round":1,"status":"pending","winner_id":null}
7. Reported the result (alice_f, id 2, wins 2-0):
   {"event_id":"fd892073-4ffa-41de-b751-5fff2f06cde5","status":"reported","winner_id":2}
8. Leaderboard now correctly shows both players:
   [{"losses":0,"rating":1020,"username":"alice_f","wins":1},
    {"losses":1,"rating":990,"username":"bob_f","wins":0}]

This confirms the result-ingestion pipeline (tournament-service ->
Redis -> ingestion-service -> Redis -> leaderboard-service) correctly
processes a result between two distinct players end to end.
